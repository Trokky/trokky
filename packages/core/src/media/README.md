# Image Processing Architecture

Trokky v2 includes a flexible, vendor-agnostic image processing system that supports multiple processing strategies from no processing at all to advanced cloud-based image transformation services.

## Overview

The image processing system is built around the `ImageProcessor` interface, allowing you to:

- **Start simple** with no image processing (store originals only)
- **Add processing later** when your needs grow
- **Switch providers** without code changes
- **Avoid vendor lock-in** with standardized interfaces
- **Deploy anywhere** including edge platforms like Cloudflare Workers

## Configuration

Image processing is configured in your `trokky.config.ts` file:

### No Processing (Default)

Perfect for simple use cases, rapid development, or performance-critical applications:

```typescript
// trokky.config.ts
export default {
  media: {
    imageProcessor: 'none' // Default - no processing
  }
  // ... other config
}
```

**Benefits:**
- Zero processing overhead
- Fastest upload times
- Works on any platform
- Minimal storage usage
- No additional service costs

### Local Processing with Sharp

For server environments where you want full control:

```typescript
export default {
  media: {
    imageProcessor: 'sharp',
    imageVariants: [
      {
        name: 'thumbnail',
        width: 200,
        height: 200,
        format: 'webp',
        quality: 80,
        fit: 'cover'
      },
      {
        name: 'preview',
        width: 800,
        height: 600,
        format: 'webp',
        quality: 85,
        fit: 'inside'
      }
    ]
  }
}
```

### Cloud Processing Services

For scalable, managed image processing:

```typescript
export default {
  media: {
    imageProcessor: 'cloudflare-images',
    imageVariants: [
      { name: 'thumbnail', width: 200, height: 200 },
      { name: 'preview', width: 800, height: 600 }
    ],
    imageProcessorOptions: {
      accountId: 'your-account-id',
      apiToken: 'your-api-token'
    }
  }
}
```

## Supported Processors

| Processor | Environment | Use Case |
|-----------|-------------|----------|
| `none` | Any | No processing, store originals only |
| `sharp` | Node.js | Local processing with full control |
| `cloudflare-images` | Any | Cloudflare's image service |
| `imagekit` | Any | ImageKit.io service |
| `imgix` | Any | Imgix service |
| `custom` | Any | Your own processor implementation |

## Image Variants

When processing is enabled, you can define variants (different sizes/formats of the same image):

```typescript
imageVariants: [
  {
    name: 'thumbnail',      // Variant name
    width: 200,             // Target width
    height: 200,            // Target height
    format: 'webp',         // Output format
    quality: 80,            // Quality (1-100)
    fit: 'cover'           // How to fit the image
  }
]
```

### Fit Options

- `cover` - Crop to fill exact dimensions
- `contain` - Scale to fit within dimensions
- `fill` - Stretch to exact dimensions
- `inside` - Scale down to fit within dimensions
- `outside` - Scale up to fit within dimensions

## Usage in Code

### Upload with Processing

```typescript
// Upload automatically processes images based on config
const mediaFile = await core.uploadMedia(file)

// Access variants if processing is enabled
const variants = mediaFile.metadata?.imageVariants
if (variants) {
  const thumbnailUrl = variants.thumbnail?.url
  const previewUrl = variants.preview?.url
}
```

### Get Image URLs

```typescript
// Get original image URL
const originalUrl = core.getImageUrl(imageId)

// Get specific variant URL
const thumbnailUrl = core.getImageUrl(imageId, 'thumbnail')
```

### Check Processing Status

```typescript
const processor = await core.getImageProcessor()
const isHealthy = await processor.healthCheck()
```

## Architecture Details

### Interface Design

All processors implement the `ImageProcessor` abstract class:

```typescript
abstract class ImageProcessor {
  abstract processImage(file: File, metadata: MediaMetadata): Promise<ProcessedImage>
  abstract getImageUrl(imageId: string, variantName?: string): string
  abstract deleteImage(imageId: string): Promise<void>
  abstract healthCheck(): Promise<boolean>
}
```

### Processing Flow

1. **Upload** - File uploaded to storage adapter first
2. **Process** - If image file, variants generated by processor
3. **Store** - Variant metadata saved with media file
4. **Serve** - URLs generated for original and variants

### Error Handling

Image processing is designed to be **non-blocking**:

- Upload succeeds even if processing fails
- Processing errors are logged but don't break uploads
- Graceful degradation to original images

## Edge Platform Support

### Cloudflare Workers

The `none` processor works perfectly on Cloudflare Workers:

```typescript
export default {
  media: {
    imageProcessor: 'none' // No Node.js dependencies
  }
}
```

For processing on Cloudflare, use `cloudflare-images`:

```typescript
export default {
  media: {
    imageProcessor: 'cloudflare-images',
    imageProcessorOptions: {
      accountId: process.env.CLOUDFLARE_ACCOUNT_ID,
      apiToken: process.env.CLOUDFLARE_IMAGES_TOKEN
    }
  }
}
```

## Custom Processors

Implement your own processor by extending the base class:

```typescript
import { ImageProcessor } from '@trokky/core'

class MyCustomProcessor extends ImageProcessor {
  async processImage(file, metadata) {
    // Your processing logic
    return {
      original: { /* ... */ },
      variants: { /* ... */ }
    }
  }

  getImageUrl(imageId, variantName) {
    // Your URL generation logic
    return `https://my-cdn.com/${imageId}/${variantName || 'original'}`
  }

  async deleteImage(imageId) {
    // Your cleanup logic
  }

  async healthCheck() {
    // Your health check logic
    return true
  }
}
```

## Migration Strategy

You can start with no processing and add it later:

1. **Development** - Use `none` for speed
2. **Testing** - Add `sharp` for local processing
3. **Production** - Switch to cloud service for scale

The same codebase works with all processors.

## Performance Considerations

| Processor | Upload Speed | Processing Speed | Storage Usage |
|-----------|--------------|------------------|---------------|
| `none` | Fastest | N/A | Minimal |
| `sharp` | Medium | Fast | High |
| Cloud services | Medium | Variable | Medium |

## Security

- All file uploads go through security validation
- Processing is done in isolated environments
- No user code execution in image processing
- Variants inherit security properties of originals

## Future Processors

The architecture supports adding new processors:

- AWS Lambda-based processing
- Google Cloud Functions
- Custom Docker containers
- AI-powered image enhancement
- WebAssembly processors

Each new processor plugs into the same interface without breaking existing code.
